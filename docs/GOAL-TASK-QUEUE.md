## Исходное состояние и выбранный путь

На baseline существовали обычный Worker и отдельные PLAN planner/worker/recovery,
предложения PLAN, специальные API, UI и голосовые состояния. Scheduler имел SQLite
jobs, один активный Worker пользователя и FIFO. `source_task_ids` давали ограниченный
контекст, но не управляли готовностью и не фиксировали полный общий результат.

Рефакторинг расширяет эти компоненты: существующий Orchestrator определяет
самостоятельные результаты в одном решении; существующий Scheduler распределяет
готовые задачи; существующий non_pipeline Worker выбирает инструменты. Goal —
запись группировки и статуса, не новый Planner или LLM-процесс. Отдельный Office
Engine и новые Office-инструменты не добавляются.

## Контракты хранения и исполнения

Расширение схемы добавляет goals, task membership, dependencies, immutable results,
request bindings, task revisions и owner capacity. Старые jobs/messages остаются.
Снимок содержит полный ответ, отчёт, journal/commands, receipt и устройства; SHA-256
проверяется при чтении. Снимок — данные источника, а не инструкции или новые права.
Подмена источника, owner/chat/goal/device, несовпадение hash и отсутствие любого
обязательного результата приводят к отказу до работы потребителя.

Небольшой материал передаётся полностью, большой — через manifest и страницы по
4000 символов. Manifest и усечённый summary не заменяют исходный материал.
Последовательное чтение всех страниц требуется до мутаций и объявления завершения.
Старые context references сами по себе не становятся execution dependencies.

`waiting_dependency` не занимает Worker. Ошибка/partial/unknown/cancelled источника
не разблокируют потребителя, независимые задачи продолжаются. Идемпотентный повтор
возвращает участников именно данного запроса, включая повтор после расширения цели.
Расширение цели и уточнение ожидающей задачи используют ревизии; работающий task
не меняется. Уточнение не наследует прежнее разрешение записи памяти и оконные
автоматические эффекты без свежего смыслового решения.

`IRU_WORKERS_PER_OWNER` по умолчанию 1, допустимы 1–4. SQLite ограничивает вместимость;
устройство резервируется целиком, включая ожидание человека. Поэтому операции на
одном ПК сериализуются; это не доказательство параллельной работы Word/PPTX на
одном устройстве. Повышение production-лимита требует отдельной приёмки изоляции.

Наличие durable dispatch marker запрещает повтор даже при нулевом значении и
противоречивом queued-статусе. Перезапуск проецирует начатые задачи в unknown;
доказанно не начатые goal-задачи могут продолжить очередь. Отмена не стирает
неизвестный исход и журнал; уточнение не обходит marker через CAS.
