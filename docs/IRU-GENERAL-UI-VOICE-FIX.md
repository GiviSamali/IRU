Исходный HEAD: `4f7982740a7ad5a6cf1bcdb16f8c1dc4b689767a`.
До отдельного разрешения пользователя commit, push, merge и PR не выполнялись. После исправления замечаний пользователь разрешил commit/push в эту ветку; merge и PR не запрашивались.

## 1. Подтверждённые причины

1. `voice.spoken_parts` после OW-01-DIALOG возвращал полный `conversational_response` Worker и полный ответ Оркестратора напрямую. Оба пути обходили `voice_brief`.
2. Интерфейс показывал состояние Worker внутри переписки. В другом чате или при прокрутке задача исчезала из поля зрения; независимого представления SQLite FIFO не было.
3. Text в Smart UI был только читаемым сообщением: не было отдельной рабочей оболочки, сохранения её раскладки и пользовательской редактируемой версии.

## 2. Этап A: голос

- `conversational_response` и исходный валидированный `answer` остаются полными; `execution_details` остаётся отдельным техническим представлением.
- `spoken_response` — отдельная кешируемая проекция на принадлежащем пользователю task. Ответ и журнал исполнения не изменяются.
- Короткие разговорные/информационные ответы до 420 символов после удаления форматирования произносятся напрямую, без редакторского LLM-вызова. Значимые inline-фрагменты сохраняются.
- Для Worker сначала применяется прежнее представление проверенного WorkerReport. Успешные действия и отрицательные исходы получают детерминированную короткую реплику; длинный информационный ответ может использовать существующий `voice_brief`.
- `voice_brief`: общий таймаут 8 секунд, max_tokens=250, входной JSON до 12000 символов, кеш по ответу/запросу/статусу. Нет исполнительных tools. Стоимость резервируется по конфигурации и известным model aliases: максимум $0.002 с учётом двух возможных HTTP-попыток общей обёртки. Это ограничение по настроенным тарифам, не гарантия фактического биллинга провайдера. Неизвестная цена, превышение бюджета, обрыв или неправильный ответ дают короткий честный fallback.
- Полное чтение включается только явной просьбой озвучить/зачитать целиком либо прочитать вслух полностью. «Прочитай файл полностью» не включает длинное чтение автоматически.
- STT, wake/sleep, очередь, десятисекундный цикл, остановка TTS и подтверждения голоса не изменены.

## 3. Этап B: Operations Dock

- Новый read-only `GET /api/operations` использует `get_current_user` и SQLite `worker_jobs` с обязательным owner filter. Возвращает активную задачу, FIFO очереди и недавние результаты; всего до 20 записей. Payload, команды и credentials в список не включаются.
- Сортировка активных/FIFO включается отдельным `queue_first=True`; прежняя сортировка `list_jobs` по умолчанию сохранена для Оркестратора.
- Статус берётся из текущего нормализованного WorkerReport либо сохранённого собственного job. `unknown`, `partial`, `failed` и `blocked` не превращаются в успех.
- Панель закреплена над областью прокрутки переписки. На desktop список расположен компактной сеткой; на телефоне — вертикальным списком. Свёрнутый индикатор остаётся виден. Панель занимает место в потоке и не перекрывает composer/микрофон.
- Различаются «В очереди» и «Нужно подтверждение». В чате Worker остаются человеческий текст, подтверждённые File-ссылки и компактный переход к операции. Большая Task-карточка и её подтверждения там не дублируются.
- Подробности загружаются только через прежний owner-guarded `/api/tasks/{task_id}`. Повторно используются `renderSmartTaskDetails`, существующий журнал, раскрытие шагов/команд и их обработчики.
- Отмена, command-decision и PLAN review идут в прежние endpoints с точными task_id, nonce/revision и auth headers. Опасные действия — только кнопкой, `via_voice=false`. Новых исполнительных endpoints нет.
- Обновление каждые 2.5 секунды, восстановление после online/visibility/pageshow; ошибки соединения видны. F5 и смена чата не запускают Worker. Раскрытие журнала и прокрутка сохраняются при обновлении.

## 4. Этап C: ContentSurface и редактор

- ContentSurface оборачивает рабочие длинные Text-блоки, не меняя четыре типа Smart UI. Приветствия и пользовательские сообщения остаются обычными.
- Масштаб 75–200%, сброс, раскрытие полного содержимого, отдельный handle и мобильные кнопки перемещения. Объект ограничен собственной областью сообщения: сдвиг до 32 px в каждом направлении от начальной позиции. Хронология не меняется; соседние подтверждения и composer не перекрываются. Это ограниченная рабочая оболочка, не свободная доска.
- Для поддерживаемых будущих DOM-объектов доступен тот же `mount`; графический fixture проверен в настоящем браузере. Новые визуализаторы документов/графиков не добавлены.
- Масштаб, положение, раскрытие и версии хранятся в localStorage с ключом пользователя, чата и устойчивого идентификатора результата. Ошибка сохранения не подменяет историю; редактор сообщает, что черновик остался в памяти страницы.
- Текст выделяется и копируется обычными средствами. Перетаскивание начинается только на handle; тело текста остаётся selectable.
- Редактор — textarea для отдельной пользовательской версии: вставка/удаление, стандартные copy/paste, Ctrl+A, Ctrl+Z/Ctrl+Y/Ctrl+Shift+Z, кнопки undo/redo, сохранение версии, явное подтверждение сброса несохранённых изменений. Закрытие сохраняет черновик, а не удаляет его.
- Original assistant message не изменяется и не отправляется обратно на сервер. Нет записи в файловую систему агента и автоматического исполнения редакторского текста. Поздний Worker update не перезаписывает открытый черновик. В другом чате редактор скрывается.
- Семантическое выделение — необязательные типизированные `highlights` в существующем Orchestrator decision: до 5 диапазонов UTF-16, start/end и kind=definition/warning/result. Они сохраняются только для соответствующего conversation/clarify answer. Сервер отбрасывает диапазоны вне ответа; UI проверяет границы/перекрытия, ограничивает виды и экранирует весь текст. HTML и произвольные CSS-классы от модели не принимаются. Выделение не предоставляет разрешений на действия.

## 7. Ограничения MVP и review

- Черновики и пользовательские версии локальны для данного браузера/профиля. Они не синхронизируются между устройствами и могут исчезнуть при очистке browser storage. Лимит одного редактируемого текста — 100000 символов; undo хранит до 50 изменений открытого редактора.
- Operations Dock показывает до 20 собственных jobs; это наблюдение за текущим FIFO, не отдельный менеджер всей истории. Обновление не мгновенное, интервал 2.5 s.
- Разметка/zoom/редактор реализованы для текста; графический объект проверен через универсальный wrapper. DOCX/PPTX renderers, canvas и агентное редактирование фрагментов не входят в FIX.
- voice_brief зависит от текущего LLM-провайдера и известных тарифов. При недоступности/лимите прозвучит честная короткая ссылка на ответ в чате, а не длинное автоматическое чтение. Качество пересказа реальной моделью и физический микрофон/TTS на Android/WebView2 здесь не проверялись.
- Diff просмотрен: новые HTTP-действия только read-only own operations; решения используют прежние owner/nonce/revision guards; модель получает лишь ranges для оформления. Raw terminal answers, WorkerReport v1, исполнительные tools, STT и исходники агента не заменены.
- Скриншоты headless Edge: `general-ui-preview-1280.png` и `general-ui-preview-390.png` рядом с предоставленным review patch. Содержимое и jobs синтетические.

## 8. Исправления после Code Review: P0 / P1

### P0: обязательная предъявленная команда и nonce

`ui/js/operations.js` больше не показывает кнопки выполнения/отклонения команды без непустой точной команды и действующего `confirmation_id`. Вместо них — сообщение о необходимости обновить состояние. Проверяются task_id, status=confirm и отсутствие PLAN review.

Кнопка привязана к предъявленному nonce и тексту команды. Перед отправкой решения интерфейс повторно читает собственную задачу и сравнивает оба значения. Если nonce, команда, статус или аккаунт изменились, POST не отправляется и пользователь должен заново проверить команду. Автоматическая подстановка нового nonce исключена. Точная исходная строка команды привязана к созданной кнопке через WeakMap; нормализация CRLF браузером не меняет проверяемую команду, а добавленная вручную кнопка не получает привязку.

Для обычного подтверждения и отклонения используется только `/command-decision` с nonce. Fallback на `/confirm` удалён. PLAN review и явная отмена задачи сохраняют собственные прежние endpoints.

### P1: сохранение DOM неизменных операций

Dock согласует отдельные строки по task_id и их фактически отображаемому HTML. Изменившаяся строка обновляется отдельно; неизменные DOM-узлы сохраняются. Технические timestamps/elapsed_ms, не влияющие на отображение, не вызывают замену узлов.

Выделение журнала, фокус, раскрытие и прокрутка неизменной задачи сохраняются при периодическом обновлении, в том числе когда обновилась соседняя операция. Изменившийся текст собственного результата обновляется честно, а не скрывается ради сохранения старого выделения.

Добавлено 10 регрессионных браузерных сценариев: отсутствующий/пустой nonce, отсутствующая/пустая команда, подставленная старая DOM-кнопка без прав на POST, смена nonce/команды/статуса после предъявления, реальный poll с выделением и фокусом на mobile/desktop, обновление соседней строки.

Проверки после review: 18 новых/текущих Dock browser tests прошли в общем наборе; 59 server confirmation/ownership/PLAN-review tests прошли. Полный JS-набор после этих исправлений — **203 passed**, 42.01 s; полный Python выше проверял общий UI/voice/OW-02 и не повторяется ради изменений только в JS.

Файлы этого follow-up: `ui/js/operations.js`, `tests/general-ui-browser.test.cjs`, данный отчёт. Предыдущие согласованные изменения UI/voice и OW-02 включаются в разрешённый commit, не удаляются.
