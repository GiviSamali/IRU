# Executor result boundary

The Worker owns execution, recovery and the substantive verdict on its Assignment.
The original human request remains the permission ceiling. Goal owns group lifecycle,
dependencies, durable results and aggregation of member statuses. Presentation does
not assess execution again.

## One terminal contract

The existing `answer_text` tool returns `status` (`success`, `partial`, `failed`,
`unknown`), compact `result`, journal-linked evidence from actual operation `step_id`s,
substantive `unresolved` requirements and material `caveats`.
The journal supplies evidence references automatically; selecting `evidence_refs`
explicitly is optional and never a mandatory bookkeeping step for the model.

The Worker compares the actual results with the original request, assigned objective,
scope, constraints and required objects. It can recover ordinary tool errors within
the same loop. Independent operations can still use Multi-tool. The loop remains
capped at 20 LLM iterations. There is no additional assessor, semantic Python goal
checker, forced verification stage or mandatory LLM verification request.

Before accepting terminal, the existing journal validator checks shape, reference
existence/ownership, success versus explicitly unfinished work, instrumental source
availability and unresolved mutation uncertainty. A contract error returns to the
same Worker loop. It does not execute an action or start another controller.
These mechanical checks do not establish semantic completeness of a user's request.
An action and a speculative terminal in the same model response cannot establish
an informed executor verdict. The already executed actions are not replayed; their
results and a terminal-contract correction are returned in the next ordinary turn.
Independent action batches still need only one normal results-to-terminal follow-up.

Owner/device/path/preservation checks and dangerous-action confirmations remain at
dispatch and execution. A transport-unknown mutation cannot be silently retried or
turned into success. Cancellation and budget termination remain runtime facts.

## Receipts and reporting

`WorkerReport` projects the accepted terminal verdict and preserves receipt provenance,
format/hash integrity and evidence references. It no longer matches Assignment file
labels, counts Office content pages or requires a second window/object acceptance
calculation to decide whether a Worker completed its Assignment.
The existing answer journal entry carries a checksum of the finalized terminal and
referenced factual records. Projection checks that those records have not changed
after the executor's decision. This is data integrity, not another completion assessment;
it adds no model call, observation, storage subsystem or execution stage.

Goal aggregates member statuses. Durable result hashes and owner checks still protect
stored dependency material. They do not interpret the requested work. Historical
bound reports remain readable without model calls, replay or migration of user tasks.
Unversioned terminals use a recorded final status as a compatibility projection.
A bare historical `done` without a bound report or explicit verdict stays unknown;
the adapter never invents a successful Assignment assessment from old tool outputs.

Version-4 terminal text is presented as executor findings; presentation does not replace
it with another interpretation of app/window receipts. The existing Orchestrator narrator
retains current-turn reply scope and owns the final conversational wording. Its existing
cache avoids repeated narration on polling, chat reload and speech.

## Ordinary document/folder opening

The existing Agent `app.launch` uses the existing OS association opener. On Windows,
this is `os.startfile`. A successful call returns `os_open_accepted=true`, the exact
`requested_object`, `launch_state=accepted` and an operation success. It does not wait
for a window or invent PID, HWND, observed document path or document loading.

`object_open_verified=false` and `observed_object=null` mean no loading observation
was performed. They do not negate OS acceptance. No follow-up window check is required
for an ordinary request to open the object. The Worker must describe only the accepted
opening request. Explicit requests to check loading, visibility or contents still need
the corresponding existing observation tools; acceptance is not that observation.

OS errors are errors. Unknown outcomes stay unknown. Arbitrary shell return code 0,
Worker prose and a matching window title are not native opening receipts. Existing
unsafe-association and executable-command policy is preserved. There are no special
WPS, PowerPoint or Adobe execution paths.

## Verification boundary

Regression tests use fake LLM responses, mocked OS calls and isolated databases. They
prove control flow, receipt semantics, status projection, group aggregation and measured
request/action counts for those fixtures. They do not prove that every real model will
interpret every Assignment correctly or that a particular installed application loaded
a document. LIVE work, production changes, installed-Agent changes and Git publication
require separate authorization.
