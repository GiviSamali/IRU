## Постоянные знания

Авторитетные данные — `knowledge/nodes.json` и `knowledge/relationships.json`, schema 1, записи по существующим stable IDs. Для узла: `what`, `why`, `how`, relationship IDs, dependency/dependent IDs, ограничения/неизвестные контракты, implementation references и метаданные проверки. Для связи: purpose, data/signals, conditions, failure behavior, interaction kind, source bindings и unknown contracts.

Это человеческие объяснения, а не дубликат семантического каталога: Semantic Catalog задаёт роли/привязки, Knowledge объясняет проблему и последовательность работы. Тексты не создают новые отношения, вершины или runtime-факты. Перечни зависимостей используют уже существующую статическую/семантическую модель, с отдельной оговоркой о runtime-критичности.

Первичное наполнение: **61 узел** — IRU, **7 подсистем / 19 компонентов / 34 механизма**. Все существующие компоненты описаны: Orchestrator; Context/Handoff; Worker; Scheduler; PLAN; Multi-device; LLM transport/routing; Tool Registry; Device Execution; Browser Bridge; Memory; State/Persistence; Authorization/Confirmation; Run Journal; Answer Auditor; Worker Report; Response Presentation; Web UI/Smart UI; Voice. Для 34 механизмов приведены отдельные what/why/how, а не одинаковые шаблоны.

Существенные человеческие объяснения подготовлены для **19 существующих отношений** между компонентами. Остальные **1 172 узла / 3 253 ребра** имеют `missing_description`; это **не полностью документированная система**. Физические реализации получили техническую справку из текущего AST/docstring/signature; она не выдаётся за ручное объяснение назначения.

`knowledge/authoring.py` хранит исходные вручную подготовленные тексты первой версии. `initialize_knowledge.py` использован один раз, отказывается перезаписывать существующие каталоги и проверяет исходные привязанные файлы относительно reviewed source. Этот bootstrap не вызывается генератором и не должен использоваться как автоматическое обновление человеческой прозы.

## Актуальность и защита от потери

`scripts/knowledge.py` читает каталоги и генерирует **только** `data/knowledge-status.json`: объединённое read-only представление, статусы, lost bindings и технические facts. `extract.py` после генерации снимка вызывает тот же build; knowledge JSON не открываются для записи. Запись generated output поверх knowledge directory или architecture.json запрещена.

Актуальность проверяется по нормализованному Python AST конкретной квалифицированной сущности либо import statement; для модульных/JS привязок — по содержимому файла. Строки и глобальный Git SHA не входят в content fingerprint. Дополнительно проверяется состав архитектурных ролей/контракта и source anchors, без номеров строк/SHA. Поэтому изменение unrelated function или commit в другой части репозитория не делает все описания устаревшими.

Статусы:

- `current` — ручное описание и связанные fingerprints согласованы.
- `missing_description` — новая/ещё не описанная сущность.
- `review_required` — changed source/contract/binding, missing reference или явно отредактированная неподтверждённая запись; текст сохранён.
- `orphaned_record` — ID исчез из текущего графа, запись остаётся в каталоге и status report.

Не выполняется перенос по имени или автоматическая перегенерация текста. При переименовании/перемещении новый ID остаётся missing, старый — orphaned, пока человек не установит достоверное сопоставление. Если binding/связанное ребро потеряно, report показывает проблему отдельно. JS/modular fingerprints шире функций: изменение такого файла может требовать консервативной проверки всех привязанных описаний.

Сохранение действует в рамках генерации/объединения атласа. Каталоги являются самостоятельными versioned assets, которые нужно сохранять вместе с приложением при переносе работы на ветки; слой не отменяет внешние Git reset/delete операции. Git History и внешнее резервное хранилище здесь не добавляются.

Редактирование одной записи без ручного переписывания всего файла:

```powershell
python scripts/knowledge.py --edit-kind nodes --id component:worker --patch approved-worker-patch.json
```

Patch изменяет только выбранную запись и ставит reviewed=false. После человеческой проверки исходников можно явно подтвердить её актуальные anchors (без замены прозы):

```powershell
python scripts/knowledge.py --review-kind nodes --id component:worker
```

Обычный пересчёт статусов: `python scripts/knowledge.py`. После изменения исходников/снимка его нужно выполнять либо пользоваться обновлённым `extract.py`; live Git tracking не добавлен. Если status sidecar не соответствует snapshot SHA, браузер сохраняет человеческие тексты, но сообщает `status_unavailable`, а не объявляет все описания устаревшими.

Текущий расчёт: **61 current node description / 19 current relationship descriptions; lost bindings = 0**. Каталоги не менялись при build. Это создание необходимого рабочего status artifact, не запуск тестового набора.

## Примеры взаимодействий

**Orchestrator → LLM transport:** передаёт untrusted context, human message и orchestrator_decision schema; проверяет единственный структурированный результат через Decision. Completion не равен admission Worker.

**Scheduler → Context:** передаёт owner/chat, original_request, devices, frozen history и source IDs для bounded messages перед выполнением job. История не становится новым разрешением или basis.

**Worker → Run Journal:** передаёт tool results и terminal payload/basis для текущих step entries и validation. Negative result или invalid basis не превращаются в completed claim.

**Presentation → Auditor:** агрегированная связь с `controller_trust.has_grounded_terminal_answer`, используемой при выборе представления. Это **не новый LLM audit call** из Presentation. В панели явно показаны тип, направление и backing evidence.

**Voice → Presentation:** получает подтверждённую основную часть ответа для spoken_parts; не создаёт отдельное исполнение и не расширяет authority.

Неописанные рёбра получают типизированную справку: contains — навигация, implements — реализация роли, import — статический импорт, static_call — найденный вызов, depends_on — агрегированная зависимость. Неизвестные data/conditions/failure behavior остаются явно неизвестными. Связь можно выбрать кликом по линии или из списка взаимодействий/доказательств; отдельная панель объясняет её, не меняя топологию.

## Человеческая панель

Название/роль → краткое what → зачем → как работает → взаимодействия → зависимости/влияние → ограничения. ID/SHA/confidence/signatures/AST/source paths и роли остаются в сворачиваемых технических разделах. What/why/how не дублируются. Состояние review и причины остаются видимыми. Для missing descriptions используется техническая справка с явным указанием отсутствия человеческого текста.

## Правый щелчок

Короткий right pointer gesture (до 450 ms, до 5 px максимального движения) на существующем видимом узле вызывает **только** `SpatialView.focus`. ID ручного выбора, A/B, details и program state не меняются. Выход и возврат указателя учитываются по максимальному движению, поэтому drag назад к старту не становится кликом.

Pointer events не перехватываются у OrbitControls: right drag продолжает pan, wheel/rotation сохраняются. Contextmenu capture подавляет default для узла/реального camera drag; на пустой области останавливает только глобальное подавление OrbitControls, позволяя обычное меню браузера. Другого контроллера камеры нет. Browser interaction tests не запускались, поэтому фактическая работа на конкретном браузере требует ручной приёмки.

## Программная подсветка

`src/highlight.mjs` вводит отдельное состояние и декларативный внутренний интерфейс `window.IRUArchitectureHighlight`:

```javascript
IRUArchitectureHighlight.highlight_nodes(['component:worker', 'component:journal']);
IRUArchitectureHighlight.highlight_edges(['depends_on:component:worker->component:journal']);
IRUArchitectureHighlight.highlight_subgraph(['component:worker'], ['depends_on:component:worker->component:journal']);
IRUArchitectureHighlight.clear_highlight();
```

Только exact IDs текущего графа; arrays ограничены 5 000 nodes / 20 000 edges. Все ID и confirmed edge classifications проверяются **до** изменения состояния. Inferred/nonexistent edges отклоняются; endpoint nodes существующих рёбер берутся из модели. API не принимает JS, Three.js commands, маршруты исполнения или network messages.

SpatialView переиспользуется; обновляются цвета/состояния существующих buffers/instances. Программная группа отмечена отдельным оттенком и легендой, не запускает pulse. Приоритет: активный Execution (включая паузу) → программный слой → текущий ручной/диагностический/статический слой. Нижние состояния сохраняются; очистка программы возвращает их. Execution stop не удаляет группу, а программный clear не стирает trace/result/selection.

Level/type/edge filters сохраняются. Если группа скрыта, предлагается явный temporary reveal отдельно от ручных temporary IDs. Clear снимает именно программные исключения. В меню «Анализ → Программная подсветка» есть группы текущих аномалий, до 10 центров по текущей метрике/порогу, механизмы Worker и компоненты безопасности.

Внешних серверных API/Orchestrator/Worker/Voice/WebSocket подключений нет. `window` namespace — внутренний интерфейс текущей локальной страницы для будущего адаптера, а не production endpoint.
